## 1. 开发顺序

不是两个 agent 各自实现一个游戏。一个包一个实现负责人，另一个做独立代码/玩法审查，必要时领取无共享文件冲突的任务。默认顺序如下，工具名称只是建议分工，可互换。

| 包 | 目标与范围 | 完成证据 | 依赖 |
| --- | --- | --- | --- |
| WP-00 初始化 | 本套规格、协作入口、React/TS/Vite 骨架、最小领域不变量 | 实际状态见 STATUS | 无 |
| WP-01 核心可玩切片 | 真实字母盘、map→mat→铺路→map、触屏/点击、步骤守卫、基本恢复、锁文件 | 可操作切片＋必要回归，不是调试按钮 | WP-00 |
| WP-02 完整故事和内容 | 十二挑战十三步、四类操作、内容结构/语义/可达性校验、帮助和学习事件 | 全流程通关＋存档恢复＋内容检查 | WP-01 |
| WP-03 音画与设备体验 | 正式资源、音频服务、绘本表现、适配/无障碍、结局/成人记录、真机问题修复 | 教研记录＋真实设备＋资源版本 | WP-01，集成依赖 WP-02 |
| WP-04 AI 关卡工坊 | 受限输入、单 Provider、预算/鉴权、校验、人工审核、预览、真实调用证据 | 一次真实造关可玩＋失败/无 API 降级 | WP-02 合同稳定；P1 |
| WP-05 参赛发布 | 必要回归、发布、提交说明、视频、真实 AI 记录 | 公开可达 Demo＋真实验收清单 | P0 完成；WP-04 可有条件关闭 |

自由野餐、动态复习与更多主题属于后续包，不挤占参赛关键路径。任何包不得把“所有阻断均因未授权 Provider”作为跳过纯前端工作的理由。

## 3. 两个 agent 的协作模型

建议 Codex 主持 WP-01 领域/会话切片，Claude Code 审查玩法因果、异常与触屏；也可对调。WP-02 时一方维护引擎/协议，另一方按冻结 schema 制作内容与 UI；不能两人都改 src/domain、内容 schema、package.json 和 lockfile。

并行使用不同 worktree 和分支，如 codex/wp-01 和 claude/wp-03-assets。开始时先读取当前 main、工作树和 STATUS；认领范围写入任务说明/PR。不要通过自动 reset、stash drop 或覆盖整个目录来解决冲突。

共享协议先提交最小变更并合并，再消费；一方尚未合并时另一方可基于明确 SHA 开发，交接时重放必要测试。不是让不同分支上的相同包各自声称“权威版本”。

## 4. 工程和完成口径

功能优先用最少足够结构实现，禁止从一周游戏扩成平台。必要测试、错误处理和类型约束不能省；大规模重构、冗余抽象和形式化报告可以省。

Implementation：代码完成范围；Validation：实际通过命令和环境；Content Review：教研/权利真实确认；Live Provider：真实调用；Device：真机；Release：公开链接。状态分列，不用一个笼统 PASS 混淆。

每包交付写明 baseline/final SHA、修改模块、玩法变化、实际测试、未运行项、阻断范围、下一包和 push/PR/merge 状态。报告中的“未运行”不能在后续合并时自动变成“通过”。

## 5. 避免常见 AI 开发失控

不要只做首页与几张漂亮卡片；不要给完整词然后称听力验证；不要动画完了才保存奖励；不要只靠 Prompt 保证关卡正确；不要为 fixture 写假 Provider SUCCESS；不要为了语音识别或后台权限阻断确定性主线；不要先建商城、排行榜、复杂后台再补游戏。

项目说明要求精确但不堆叠：根 AGENTS.md 为共同规范；CLAUDE.md 引用它；每个工作包关注目标、边界和验收，具体组件拆分由实现者判断。
